# Business API Guidelines

## Contract bootstrap approach

The foundation defines API behavior and conventions before backend implementation. During initial backend development, NestJS and Better Auth generate the first machine-readable OpenAPI documents. Those documents are reviewed, approved and committed here. After approval, subsequent backend changes must conform to the committed contracts.

Do not fabricate a complete OpenAPI file before actual endpoints and DTOs are designed. Do not allow the backend to invent behavior that conflicts with the product/domain requirements.

## Business API conventions

- Base path: `/api/v1`.
- JSON field naming: camelCase.
- Success envelope: `{ "data": ..., "meta": ... }`.
- Collection responses include cursor metadata in `meta`.
- Error responses: RFC 9457 Problem Details, extended with stable `code` and `traceId`.
- Dates: ISO 8601; timestamps UTC; calendar dates are `YYYY-MM-DD`.
- `null`, omitted and false/zero/empty string are distinct.
- PATCH must distinguish omitted field from explicit null.
- Cursor-first pagination; stable ordering with tie-breaker.
- Shared filtering/sorting syntax, allowlisted fields only.
- Example: `?status=active&sort=-createdAt&limit=20&cursor=...`.
- Tenant authorization and scoping occur before pagination.
- Idempotency keys required for critical writes.
- HTTP 429 is used for rate limiting with `Retry-After` where applicable.
- Auth endpoints retain Better Auth's own response schema and behavior.

## Idempotency

Required for critical operations such as:
- Payment recording/confirmation where retry ambiguity exists.
- Attendance check-in.
- Subscription assignment and renewal.
- Owner invitation creation.

Rules:
- Store key, actor/scope, request fingerprint and original outcome in PostgreSQL.
- Same key and same payload returns the original result.
- Same key with different payload is rejected.
- Key record and business operation are transactionally coordinated.
- Define retention/expiry and ensure it exceeds practical client retry windows.
- Idempotency is not a substitute for database uniqueness constraints.

## API versioning and mobile compatibility

- `/api/v1` for current business API.
- Additive compatible changes may remain in same version.
- Breaking changes require a new major API version.
- Maintain compatibility with supported older mobile versions.
- Raise minimum supported app version before removing behavior required by older supported clients.
- Remote app policy is per application: latest version, minimum supported version, update-required state, message and store URL.
- Test API contract compatibility against supported released app versions.

## OpenAPI ownership

- Gym business API: generated by NestJS Swagger from DTOs/controllers.
- Better Auth: generated using Better Auth OpenAPI plugin/configured schema endpoint.
- Keep the two specifications separate.
- Commit approved specs under `04-api/openapi/`.
- KMP generation consumes approved specs with separate packages for auth and business APIs.
- CI validates implementation-generated business OpenAPI against the canonical committed contract after bootstrap.
- Generated client code must not be hand-edited.

## API tooling

- Swagger UI in Development and Staging.
- Production Swagger UI disabled or access-restricted.
- Bruno collections version-controlled in `gym-backend`.
- API tests must include tenant authorization and critical business lifecycle cases.
